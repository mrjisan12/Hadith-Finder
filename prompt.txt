# Project: Hadith Source-Grounded AI RAG Chatbot

I want you to build a professional, production-quality MVP of a source-grounded AI chatbot based on a scanned Hadith/Islamic book PDF.

The primary goal is NOT to build a generic "chat with PDF" application.

The core goal is:

> When a user asks a question about a topic, the system should retrieve the most relevant passage from the original book and show the exact original paragraph/text together with the book's printed page number and the corresponding PDF page. The user should also be able to view the original scanned page to verify the source.

The original PDF must remain the ultimate source of truth.

---

# 1. Source Document

I will provide a scanned PDF of approximately 1009 pages.

Example:

source/fazail-e-amal.pdf

The PDF may contain scanned pages rather than machine-readable text.

The system must preserve:

* PDF page number
* Printed page number
* Chapter/section where available
* Exact paragraph
* Paragraph order
* Original page image
* Source document/book ID

Important:

The PDF viewer page number and the printed page number may NOT be the same.

For example:

PDF page: 263
Printed book page: 251

The application must preserve both values.

---

# 2. Core Product Behavior

Example user query:

"সদকার ফজিলত সম্পর্কে কী বলা হয়েছে?"

The system should:

1. Understand the user's question.
2. Search the indexed book.
3. Retrieve relevant passages.
4. Perform hybrid retrieval using semantic/vector search and keyword/full-text search.
5. Rerank candidate passages.
6. Select the most relevant source passages.
7. Generate a concise answer based ONLY on the retrieved sources.
8. Return the exact original source passage from the database.
9. Show:

   * Book name
   * Printed page number
   * PDF page number
   * Chapter/section if available
   * Exact original paragraph
10. Provide a "View Original Page" feature that displays the scanned page image.

The application should make it easy for a user to verify that the quotation actually exists in the source.

---

# 3. Critical Anti-Hallucination Requirement

This is extremely important.

The LLM must NEVER be treated as the source of the original quotation.

Do NOT allow the LLM to freely generate or reconstruct quoted source text.

The architecture should be:

User Query
→ Retrieval
→ Reranking
→ Source IDs
→ LLM answer generation
→ Backend retrieves ORIGINAL stored text using source IDs
→ Frontend displays ORIGINAL database text

The quotation displayed under "Original Source" must come directly from the database/OCR source text, not from the LLM's generated response.

The LLM may summarize or explain retrieved content, but source quotations must come from stored source data.

Supabase will be used as the PostgreSQL hosting platform.

Design a proper relational schema.

At minimum consider:

embeddings

A source chunk should contain enough metadata to trace it back to the exact original page.

For example:

{

"paragraph_index": 4,

Use proper foreign keys and indexes.

Do not store the entire PDF binary inside PostgreSQL.

# 8. OCR / Document Ingestion

Create a robust ingestion pipeline.

Pipeline:

PDF
→ page extraction
→ high-resolution page image
→ OCR
→ text cleaning
→ paragraph/section detection
→ page mapping
→ database insertion
→ embeddings

The ingestion pipeline should preserve page boundaries.

Do NOT combine the entire PDF into one giant text document.

Paragraph-level or semantically meaningful chunks should be created while retaining:

* page number
* paragraph number
* section/chapter
* source document
* original image reference

If OCR supports bounding boxes, preserve bounding-box information because it can later be used to highlight the source text on the original scanned page.

---

# 9. Printed Page Number Detection

This is an important requirement.

The application must distinguish:

PDF page number

from

printed book page number.

If printed page numbers are visible in the scan, create a mapping:

pdf_page_number
→ printed_page_number

Do not assume they are identical.

Create a mechanism for correcting the mapping manually if OCR fails.

For example, provide an ingestion/configuration file such as:

page_mapping.json

or a database table that allows:

PDF page 263 → printed page 251

This mapping must be used by the citation system.

---

# 10. Chunking

Do NOT blindly use arbitrary fixed-size chunks.

Prefer document-aware chunking.

Ideally:

Book
→ Chapter/Section
→ Paragraph
→ Sentence

A paragraph should preferably remain intact.

If a paragraph is too large, split it while retaining a parent/source relationship.

Every chunk must maintain its source page relationship.

---

# 11. Retrieval

Use hybrid retrieval.

Do NOT rely only on vector similarity.

Recommended:

1. Vector similarity search using pgvector.
2. PostgreSQL full-text/keyword search.
3. Combine candidate results.
4. Rerank candidates.
5. Return top relevant passages.

Example:

Question
→ vector search: top 20
→ keyword search: top 20
→ merge/deduplicate
→ reranker
→ top 3–5 passages

The retrieval implementation should be modular so the embedding model or reranker can be replaced later.

---

# 12. Embeddings

Use a strong multilingual embedding model/API suitable for:

* Bangla
* English
* Arabic/Islamic terminology where relevant

Keep embedding generation inside the ingestion pipeline.

Do not regenerate embeddings every time a user asks a question.

Store embeddings in pgvector.

---

# 13. Reranking

Use a multilingual reranker where practical.

The goal is:

Vector/keyword search
→ candidate passages
→ reranker
→ highly relevant source passages

Keep the reranker service modular.

If the chosen reranker is too expensive for the MVP, provide a simpler fallback while keeping the architecture ready for a production reranker.

---

# 14. LLM

Use the API credentials I provide.

The LLM should be used for:

* Query understanding
* Answer synthesis
* Summarization
* Explanation
* Identifying relevant retrieved context

The LLM must NOT invent source citations.

Every source citation must correspond to a real source record returned by the retrieval system.

If the retrieved evidence is insufficient, the assistant should say that the source material does not provide enough evidence rather than hallucinating an answer.

---

# 15. Citation Architecture

Every source chunk should have a stable source ID.

Example:

chunk_8f72a

The LLM can return source IDs, but the backend must validate them.

Backend should:

1. Receive source IDs.
2. Verify they exist.
3. Retrieve original stored text.
4. Retrieve book/page metadata.
5. Return verified source objects to frontend.

Example response:

{
"answer": "...",

"sources": [
{
"source_id": "chunk_8f72a",
"book": "Fazail-e-Amal",
"printed_page": 251,
"pdf_page": 263,
"section": "...",
"original_text": "...",
"page_image_url": "..."
}
]
}

The frontend should display `original_text` from this verified backend response.
